COMO CONECTAR CON TABLEPLUS
  Las BD 1 a 3 no tienen IP publica (servicios internos, ClusterIP): abre un tunel con kubectl port-forward en una
  terminal, dejala abierta, y en TablePlus usa Host 127.0.0.1 + el puerto local.

  - comensales_reservas (Azure):
      kubectl --kubeconfig comedor-infra/respaldo/kube-aks.yaml -n comedor port-forward svc/postgres-comensales 5433:5432
                                                                           -> TablePlus: PostgreSQL 127.0.0.1:5433
  - pagos_tickets (GCP):
      gcloud container clusters get-credentials comedor-gke --zone us-central1-a --project <TU_PROYECTO_GCP>
      kubectl -n comedor port-forward svc/postgres-pagos 5434:5432         -> TablePlus: PostgreSQL 127.0.0.1:5434
  - menu_inventario (AWS):
      aws eks update-kubeconfig --region us-west-2 --name comedor
      kubectl -n comedor port-forward svc/mongo 27017:27017                -> TablePlus: MongoDB 127.0.0.1:27017, base menu_inventario, Auth DB = admin
  - Usuario/clave de cada Postgres y de Mongo: kubectl -n comedor get secrets  (y ver el que usa cada manifiesto).
  - agentes.db (SQLite, AWS): no se abre por tunel; se copia el archivo y se abre en TablePlus como SQLite:
      aws eks update-kubeconfig --region us-west-2 --name comedor
      kubectl -n comedor get pods                  (el que empieza con ia-ml-service)
      kubectl -n comedor cp <pod-ia-ml-service>:/data/agentes.db ./agentes.db
      (la copia es una foto del momento; los cambios que hagas en ella NO vuelven al pod)
  - DynamoDB (real, sin tunel): consola de AWS > DynamoDB > Tablas (region us-west-2) o 'aws dynamodb scan --table-name sagas'.

NOTAS DE LECTURA
  - TIPOS CORTOS: uuid, varchar(255), text, json, int, float, decimal(10,2), bool, date, timestamp, enum.
    varchar(255) = texto corto (el 255 es solo para el diagrama). json = JSON. enum = valores fijos (ver columna 'valores / nota').
  - CLAVE / RELACION:  PK y UNIQUE.
      FK            = clave foranea dentro de la misma base de datos.
      FK(otra BD)   = apunta a otra base (cada servicio tiene la suya): se dibuja como relacion entre servicios.
      FK(externa)   = apunta a un usuario de Keycloak (sistema aparte; no es una tabla de estas bases).
  - [CAMBIO] = cambio respecto a lo desplegado.  [NUEVO] = tabla, coleccion o columna que no existe hoy.
  - Los nombres de columna de comensales_reservas van en camelCase (TypeORM): en SQL van entre comillas dobles.
  - [SOLO EN CODIGO] = tablas que el codigo crea pero no estan en el respaldo del 8-nov.
  - Al final: RELACIONES (para el diagrama) y CAMBIOS APLICADOS.

RELACIONES (para el diagrama)   formato: tabla_A  cardinalidad  tabla_B   (columna que las une)
====================================================================================================

  Dentro de comensales_reservas
    estudiantes 1 ---- N becas                        (becas.estudianteId -> estudiantes.id)

    pagos 1 ---- 0..1 tickets                         (tickets.pago_id -> pagos.id)

  Dentro de menu_inventario
    platos 1 ---- N porciones de menu                 (menus.porciones[].platoId -> platos._id)

    platos 1 ---- N ingredientes                      (platos.ingredientes[]; cada uno -> insumos._id)
    insumos 1 ---- N lotes                            (lotes dentro del documento insumo)

  Dentro de agentes.db
    chats 1 ---- N outbox                             (outbox.chat_id -> chats.chat_id)
    propuestas 1 ---- N outbox                        (outbox.propuesta_id -> propuestas.id)
    chats 1 ---- N pagos_tg                           (pagos_tg.chat_id -> chats.chat_id)
    ref_porcion 1 ---- N bandejas                     (bandejas.ref_id -> ref_porcion.id)

  Dentro de DynamoDB
    sagas 1 ---- N idempotency_keys                   (idempotency_keys.sagaId -> sagas.sagaId)

  Entre bases de datos (se dibujan como relaciones entre servicios)
    reservas N ---- 1 menus                           (reservas.menuId -> menus._id)        comensales_reservas -> menu_inventario
    reservas N ---- 1 platos                          (reservas.platoId -> platos._id)      comensales_reservas -> menu_inventario
    pagos N ---- 1 reservas                           (pagos.reserva_id -> reservas.id)     pagos_tickets -> comensales_reservas
    pagos N ---- 1 estudiantes                        (pagos.estudiante_id -> estudiantes.id)
    obligaciones_proveedor N ---- 1 propuestas        (orden_id -> propuestas.id)           pagos_tickets -> agentes.db
    pagos_tg 1 ---- 1 reservas                        (pagos_tg.reserva_id -> reservas.id)  agentes.db -> comensales_reservas
    ref_porcion N ---- 1 platos                       (ref_porcion.plato_id -> platos._id)  agentes.db -> menu_inventario
    bandejas N ---- 1 platos                          (bandejas.plato_id -> platos._id)     agentes.db -> menu_inventario

  Sin relaciones: config

CAMBIOS APLICADOS (modelo corregido frente a lo desplegado)
====================================================================================================

   1. becas.estudianteId y reservas.estudianteId: varchar -> uuid, con FK a estudiantes.id.
   2. pagos.reserva_id y pagos.estudiante_id: texto -> uuid (siguen siendo relaciones entre bases).
   3. Se quito pagos.ticket_id; la relacion pago-ticket queda solo en tickets.pago_id (uuid, UNIQUE, FK a pagos.id).
   4. Se quitaron tickets.reserva_id y tickets.monto (se obtienen por pago_id).
   5. Nueva coleccion platos (_id, nombre, ingredientes[] con insumoId y cantidad). menus.porciones[].platoId,
      reservas.platoId, ref_porcion.plato_id y bandejas.plato_id apuntan a ella. Es una PROPUESTA: hoy no hay platos.
   6. Nueva tabla proveedores; obligaciones_proveedor.proveedor (texto) -> proveedor_id (uuid, FK).
   7. Los usuarios viven en Keycloak: asistencias.usuario, chats.username y dispositivos.usuario quedan marcados
      como FK(externa) en vez de inventar una tabla de usuarios.
   8. menus.porciones: de mapa (platoId repetido) a array de porciones.
   9. insumos.lotes[]: se quito la unidad repetida y la fecha pasa a lotes[].fechaVencimiento (date).
  10. agentes.db: FK declaradas en outbox (propuesta_id, chat_id), pagos_tg (chat_id) y bandejas (ref_id).
  11. agentes.db: fechas float/texto -> timestamp/date; con_botones int -> bool; payload, roles, ctx -> json.
  12. pagos_tg: se quitaron plato, fecha y turno (se obtienen de la reserva). En bandejas se dejaron plato_id, fecha y
      turno: no pude confirmar que siempre igualen a los de ref_porcion.
  13. turno, estado, tipo y metodo pasan a enum con sus valores. 'rol' queda varchar: no conozco todos sus valores.
  14. idempotency_keys: columna nueva sagaId (FK a sagas.sagaId), para no depender del JSON.

  NO APLICADOS (a proposito)
   - 'con beca activa solo una racion por dia': es una regla de negocio condicionada a la beca (ReservarRacion.ts);
     no se expresa con un UNIQUE simple, asi que sigue en el codigo.
   - Factura: existe Domain/Factura.php pero no se guarda en la BD; no la agregue porque no se que campos lleva.
